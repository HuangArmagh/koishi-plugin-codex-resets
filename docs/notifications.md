# 推送规则与数据持久化

仅向通过指令订阅的会话主动推送。消息样式见[主动推送文案](notification-messages.md)，操作方式见[使用与配置](usage.md)。

## 事件、基线与去重

- **重置预告**：来自 `scheduled_reset`，表示网站记录了明确公告，仍待执行证据。新订阅首次检查推送当前预告；后续新预告按重置类型与 ID 去重。相同预告的文字或预定时间变化仅刷新未发送记录，保留重试次数和退避；已发送的不重复推送。预告消失、被新预告替代或确认执行时取消未发预告；重启后先用状态校验再恢复重试。预定时间可以为空，时间已到也不自动认定执行。
- **概率预测**：`active_watch` 仅在状态查询中显示，不入主动推送队列，包括概率为 100% 的情况。
- **已执行重置**：每个新订阅周期先使用注册后发起或重新验证的状态请求，并完成一次覆盖注册以来历史的补查，再结束初始化。即使最新记录使用较早的原公告时间、最新记录为空或其他会话已推进全局检查点，也不能跳过这次补查；首次状态请求失败后恢复同样适用。默认不补发订阅前已有的重置；初始化未完成时保留进度，按共享退避规则继续补查。待发记录全部写入成功后才保存初始化结果，写入中断后恢复并复用已入队记录。建立基线后，新出现的已执行重置会推送，即使它保留了较早的原公告时间。消息区分常规重置和储备重置。
- **初始化旧记录排除**：完整补查中，某事件的所有关联记录均早于注册，且当前订阅未跟踪该事件的待执行公告时，将它加入该订阅的排除基线。后续状态回退到这些旧记录或切换关联 ID，也不误发；该基线随订阅持久化并在重启后保留。任一页失败时不提前保存这类排除，避免后续页里的较晚观察记录被遮掉。
- **后续执行跟踪**：预告通知和已执行通知使用不同事件标识。每个订阅会保存自己观察到的待执行公告；重启后继续补查，只有最新重置或历史接口确认执行后才推送，即使期间又出现了更新的重置。公告消失或预定时间已到都不代表执行完成。
- **预告与观察记录关联**：最新重置或历史记录的 `source.type` 为 `observed`，且 ID 完整符合 `observed-<数字公告ID>` 时，将其关联到同一重置类型的原公告 ID。例如 `observed-2114588174249071102` 可确认公告 `2114588174249071102` 已执行，并清除对应的待确认记录；不同公告 ID、不同重置类型和非 `observed` 来源不按此前缀关联。关联后的执行证据会持久化，避免旧预告重新出现时再次推送。
- **关联事件去重**：同一执行事件在状态和历史中分别使用原 ID 与 `observed-` ID，或后续切换 ID 时，每个订阅周期只保留一次有效投递。关联会持久化并双向用于基线、检查点和通知去重。先保留关联组内各条记录的时间，分别判断当前会话是否应接收，再选取一条符合条件的记录投递；状态记录符合条件时优先采用状态记录。原 ID 的时间早于订阅，不会遮掉订阅后才出现的执行记录，也不会将整组误记为订阅前基线；注册前已确认的事件仍整组排除。选定的通知按记录时间排序。已有通知沿用原 ID、发送结果、重试次数和退避时间。若旧队列已有两个关联记录，提交发送前优先保留已成功记录并取消尚未发送的重复项；都未成功时使用最早创建的记录。结果尚未返回的发送仍等待原调用，不因 ID 切换另发一条。
- **旧订阅自动恢复**：升级时从数据库中有效的已执行通知原始数据恢复关联，要求记录内容通过校验且 ID 与投递记录一致。即使最新重置已推进，只要当前会话、当前订阅周期已有对应投递记录（已发送或等待重试），就可清理旧预告跟踪；注册基线已排除的旧事件也可清理，无需清库或重新订阅。尚未发送的执行通知继续保留和重试。其他会话、其他订阅周期或仅有全局执行证据时，不能据此丢弃当前会话尚未入队的提醒；旧数据缺少有效内容时仍需从状态或历史确认。
- **必要补查保留**：清理后的旧公告不再单独触发历史请求；已有检查点只发生已关联 ID 切换时，也不再视为新的执行事件。新预告独立处理，真正出现新执行事件或仍有未完成跟踪时继续补查中间记录。必要历史校验失败时保留检查点并暂缓预告。
- **空状态恢复**：`latest_reset` 暂时为 `null` 时保留最后有效检查点，不用空快照的时间替换历史补查起点。最新记录恢复后，继续覆盖中间记录，并沿用原有去重结果；重启后同样适用。没有有效检查点或旧数据仅保存了空检查点时，从最早仍有效的订阅时间补查，并继续覆盖待确认公告的更早时间。连续空状态本身不会反复触发历史请求；新订阅初始化及尚未确认的公告仍按原规则补查。
- **执行证据保留**：后台确认的执行标识独立持久化，优先于状态接口中残留的同一预告；通知尚未发送或当前订阅已取消也不会丢失证据。
- **注册时执行基线**：新订阅记录注册前已确认的事件；这些事件即使再次出现在 `latest_reset` 或历史中，也不为该订阅周期生成已执行通知。基线随订阅持久化，语言变更不会重置。

## 轮询、持久化与重试

- 订阅、待执行公告跟踪、发送记录及 API 请求时间、退避截止时间保存在 Koishi 数据库，重启后继续使用。重复注册不会重复创建订阅，取消订阅后重新注册会开启新的订阅周期。
- 没有订阅会话时，后台不会请求网站。手动状态查询仍可按需请求，并复用缓存。
- 开启订阅会请求一次尽快检查；重复操作保留更早的待执行检查，不延后正常轮询。若检查正在进行，多次请求合并到完成后的一次检查，仍遵守网站请求间隔与退避。
- 同一进程中的所有订阅共享 API 采集结果；发生新重置时，通过时间过滤和游标分页补查中间记录。需要补查时，起点同时覆盖已观察且尚未确认执行的公告原时间，即使该公告仍显示为当前预告；历史按公告时间筛选，不能只用订阅时间截断。初始化完成后，稳定预告本身不会额外触发历史查询。单次最多补查 2000 条，异常时保留检查点并记录日志。
- 发送失败按目标单独退避重试，所有批次共用发送间隔。轮询先校验状态及补查证据，再放行仍有效的预告；状态或必要历史校验失败、API 退避期间保留预告队列并暂停其发送，已执行重置仍可正常重试。最终订阅检查和提交发送与取消操作按顺序执行；取消订阅确认后，不再提交该订阅周期的排队消息。已经进入适配器发送流程的消息无法撤回，但等待适配器返回不会阻塞取消订阅。
- 单次适配器调用等待超过 30 秒后，继续处理其他会话及后续轮询；同一会话暂停提交后续消息，直到原调用真正返回。超时只结束等待，不会把结果未知的调用当作失败重发。迟到成功写入发送记录，迟到失败按正常退避重试；已读队列在发送前重新校验，避免迟到结果造成重复。此跟踪仅在当前进程内有效，重载或重启不能撤回平台已收到的请求；平台已接收但确认丢失等异常情况下，重试仍可能导致重复消息。

运行 Koishi 时请仅启用一个采集实例；多个进程共享数据库时尚未提供分布式投递锁。使用持久化数据库才能保留重启前的订阅和发送记录。

API 的请求间隔、缓存、限流退避及未完成请求的恢复步骤见 [API 与故障恢复](api.md)。

QQ 官方适配器的主动发送额外按至少 3100 毫秒间隔提交，URL 正常保留；仅在明确返回 URL 禁用错误时才尝试一次保留来源名称的通知。每次等待结束后，包括 URL 降级重试，重新按顺序校验订阅周期、待发记录与预告有效性，并使用最新订阅语言生成文案；检查和提交发送共用取消操作的顺序锁，等待 HTTP 结果时释放锁。已经撤销的预告不会发送，暂未完成校验的预告保留等待。详见 [QQ 接口与频控](platforms.md#qq-官方适配器)。发送失败日志会展开嵌套异常并显示已有的 HTTP 状态、平台错误码和原因；日志格式及排查方向见 [投递故障排查](docker-qq-testing.md#7-排查问题)。
